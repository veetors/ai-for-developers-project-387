# Доставка schedule-события GitHub Actions: диагноз и смена расписания

## 🎯 Проблема
В `.github/workflows/opencode-scheduled.yml` настроен `on: schedule` (повторяющаяся
Lighthouse-проверка). После коммита `009cab0` (добавление workflow, ~11:18 UTC) и
нескольких часов ожидания GitHub **ни разу** не создал schedule-ран. Вкладка Actions
показывала только 2 ручных запуска (`workflow_dispatch`). Ожидалось, что ежечасный
cron `17 * * * *` сработает в 12:17, 13:17, 14:17 UTC… — ни одного не появилось.

## 🔍 Диагностика (read-only, через GitHub REST API)

| Проверка | Результат | Вывод |
|---|---|---|
| `actions/runs?event=schedule` по всему репо | `total_count: 0` | GitHub не создал ни одного schedule-рана — ни для Lighthouse, ни для удалённого `cron-probe.yml` (`*/10`, жил 47 мин) |
| Все раны `opencode-scheduled.yml` | 2 шт., оба `workflow_dispatch` | Только ручные запуски |
| `actions/workflows/opencode-scheduled.yml` | `state: active`, путь `.github/workflows/...` | Workflow включён, не disabled |
| Файл на default-ветке | `git branch -r --contains` → `origin/main` ✓ | Schedule-триггер читается с `main` |
| Репозиторий | Public, **не fork** (нет «forked from»), активный (коммиты в этот же день) | Исключает: fork-disable, 60-дневную неактивность, private/spending |
| Cron `17 * * * *` | Валидный POSIX, минута `:17` вне top-of-hour | Синтаксис и выбор времени корректны |

**Что исключено с доказательствами:** файл не на `main`, fork, неактивность 60 дней,
отключённый workflow, приватность/лимит минут, синтаксис cron, DST/часовой пояс.

## ✅ Корневая причина
Конфигурация корректна — проблема на стороне GitHub: планировщик не доставляет
`schedule`-события этому репозиторию. Два задокументированных фактора 2026:

1. **Деградация доставки schedule в 2026.** actions/runner issue #4468 (июнь 2026):
   schedule-раны задерживаются на 4+ часа или **полностью дропаются без следа**
   (нет ни строки в UI, ни письма). Множество источников май–авг 2026 подтверждают,
   что schedule-раны часто вообще не создаются — absence выглядит как success.
2. **Разогрев свежего schedule-триггера.** Workflow с `schedule:` добавлен всего ~3ч
   назад. Новый schedule регистрируется планировщиком не мгновенно, а на фоне
   деградации 2026 свежий триггер мог просто не подхватиться. `*/10`-проба жила лишь
   47 мин — слишком мало, чтобы поймать доставку при текущих задержках.

## 🛠 Решение
Переход с hourly (`17 * * * *`) на **daily в off-peak окне** — `17 1 * * *`
(**04:17 МСК**, 01:17 UTC):

- **Off-peak час `01` UTC** попадает в рекомендованное окно 18:00–04:00 UTC — меньше
  конкуренции в очереди планировщика, ниже шанс дропа.
- **Нечётная минута `:17`** вне «top-of-hour» (`:00`), где GitHub дропает раны чаще
  всего (документировано: «High load times include the start of every hour»).

Это осознанный компромисс: команда отказалась от внешнего триггера, поэтому
полностью исключить дропы невозможно — но daily off-peak минимизирует их вероятность
относительно ежечасного запуска. Минута `:17` оставлена намеренно против ровно `04:00`.

## 🚀 Как верифицировать
Единственный способ проверить нативный `schedule` — дождаться слота и посмотреть API.

1. После merge этого коммита в `main` следующий слот — **завтра ~04:17 МСК (01:17 UTC)**.
   GitHub допускает задержку до 15+ мин (при деградации — дольше).
2. Проверить доставку:
   ```bash
   curl -fsS "https://api.github.com/repos/veetors/ai-for-developers-project-387/actions/runs?event=schedule" \
     | python3 -c "import sys,json; print(json.load(sys.stdin)['total_count'])"
   ```
   `total_count > 0` → schedule-доставка работает.
3. Ручной `workflow_dispatch` остаётся рабочим fallback (Actions →
   **Scheduled OpenCode Task (Lighthouse)** → Run workflow) — независим от
   schedule-доставки.

## ⚠️ Риск и откат
Из-за разогрева после правки cron + деградации 2026 первый schedule-ран может не
прийти в первый/второй день. Это **не баг нашей конфигурации** — особенность платформы.
Если спустя ~2 суток `total_count` всё ещё `0`:
- ручной запуск покрывает потребность в отчёте, пока schedule «прогревается»;
- возврат к обсуждению (возможные пути: внешний триггер через Render Cron/cron-job.org
  → `workflow_dispatch`; или оставить только ручной запуск).
